Confirm or configure CORS on all Cairn backend services so browsers can call them with an Authorization header.

SCOPE: User Service (/api/v1/auth/*), Read Service (/api/v1/content/*), Explore Service (/api/v1/explore/*), Email Ingest (/api/v1/source/email/*).

WHAT TO DO:
- Audit each service's HTTP middleware for Access-Control-Allow-Origin, Access-Control-Allow-Headers (must include Authorization), Access-Control-Allow-Methods.
- Add/update CORS middleware to allow the web origin (initially * or the deployed domain) plus handle preflight OPTIONS requests.
- Deploy and smoke-test from a browser.

VERIFICATION (agent-testable):
1. From a browser console on the web app origin, run: fetch('https://cairn.seatrain.net/health/live'). Expect 200 with no CORS error.
2. Preflight OPTIONS to POST /api/v1/auth/login with Origin and Access-Control-Request-Headers: authorization,content-type returns 200/204 with Access-Control-Allow-Origin and Access-Control-Allow-Headers containing 'authorization'.
3. A full login POST from the web app (fetch with mode:'cors', Authorization header) succeeds without a CORS error in the browser console.

## Audit findings (2026-06-08)

Public/browser-facing routing is via the prod Caddy reverse proxy (`infrastructure/docker/prod/Caddyfile`); the selfhost binary (`cmd/selfhost`) is the alternate single-binary deployment. Internal services (explore-fetcher `/api/v1/explore/feed/*`, ingest-rss `/api/v1/source/rss/*`, `/api/v1/internal/*`) are blocked at the proxy → out of scope.

Browser-facing services and prior CORS state:
- User Service (`/api/v1/auth/*`, `/api/v1/user/*`, `/health/*`): CORS applied but only inside the `/api/v1` group → `/health/*` (which Caddy routes to user-service) had NO CORS, and preflight relied on chi sub-router middleware running for an unregistered method.
- Content Service (`/api/v1/content/*`): no CORS.
- Explore Recommender (`/api/v1/explore/*`): no CORS.
- Email Ingest (`/api/v1/source/email/*`): no CORS.

A reusable `pkg/middleware.CORS` already exists (`DefaultCORSConfig` = origin `*`, methods GET/POST/PUT/PATCH/DELETE/OPTIONS, headers incl. Authorization, handles preflight). Cairn uses Bearer-token auth (no cookies), so wildcard origin + `AllowCredentials:false` is correct and matches the existing user-service config.

## Plan

2. [x] Content Service: add top-level `CORS` → compiles
3. [x] Explore Recommender: add top-level `CORS` → compiles
4. [x] Email Ingest: add top-level `CORS` → compiles
5. [x] Selfhost binary: add top-level `CORS` on master router (covers aggregated `/health/*` + all in single-binary mode) → compiles
6. [x] Add chi-integration test proving top-level CORS handles preflight OPTIONS (204 + Authorization in Allow-Headers) and applies ACAO to a GET route with no OPTIONS handler → `go test ./...` passes

Note: chi runs top-level `Use` middleware before route/method resolution, so a top-level CORS middleware intercepts `OPTIONS` before chi's 405 handling and applies headers to every response (incl. health). This is why placement is top-level rather than inside route groups.

NOTE: deploy + browser smoke-test (verification steps 1-3 against cairn.seatrain.net) require a live deployment and cannot be run from this environment; covered locally by the chi-integration test.
