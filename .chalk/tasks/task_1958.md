## Problem
The users service's DB-backed tests cannot run, for **two independent reasons** — fixing either one alone leaves them dead:
1. **No Postgres in CI.** `.github/workflows/go-checks.yml`, job `test-users`, runs `go test ./internal/...` with **no `services: postgres` block** — unlike `test-integration-read`, which provisions postgres:16-alpine and sets TEST_DB_*. Any test needing a database cannot pass.
2. **The env helper is a stub.** `getEnvOrDefault` is triplicated across three files and **ignores `os.Getenv` entirely**:
   - services/users/internal/database/user_repository_test.go:43
   - services/users/internal/services/auth_service_test.go:80
   - services/users/internal/handlers/auth_handler_test.go:104
   All three bodies are literally:
   ```go
   // In real implementation, use os.Getenv
   return defaultValue
   ```
   So even with a Postgres service container and TEST_DB_* exported, the tests would still dial the hardcoded defaults and ignore the CI environment.

## What to do
1. Add a `services: postgres` block to `test-users`, mirroring `test-integration-read`'s (health-cmd pg_isready, TEST_DB_HOST/PORT/USER/PASSWORD env).
2. Replace all three `getEnvOrDefault` copies with one real implementation that reads `os.Getenv`. Prefer reusing the existing shared helper over a fourth copy — see task_7ada (pkg/env vs pkg/config consolidation) and don't fight it.
3. Expect red on first enablement — that is the finding, not a regression. Triage what fails.

## Done when
- `test-users` provisions Postgres, the env helper honours TEST_DB_*, and the DB-backed tests actually execute in CI (pass or triaged failures, not silently skipped).
