## Problem
`ArticleMutations` (`apps/mobile/src/services/articleMutations.ts`) writes the store, sends the request live, and enqueues only on a retryable failure. A live success never looks at the outbox, so an older queued edit of the same field can replay afterwards and win.

## Reproduce
1. Offline: favourite an article. The store holds `true` and the outbox holds `is_favorite: true`.
2. Back online, before `SyncTrigger.run` drains (the reconnect transition has not fired yet, or the drain halted on an earlier row): unfavourite it. The live PATCH `false` succeeds.
3. The drain replays `is_favorite: true`. The server ends on `true`, and the next list sync writes `true` back to the store.

The same applies to `status`, `scroll_position` and `list`.

A second, related defect: `Outbox.drain` deletes a row after sending it without checking that the payload is still the one it sent, so an edit coalesced into the row while the request was in flight is lost.

## Notes
- Found while planning the native iOS port (decision 9 in decision_adb1), which avoids both by making the outbox the only write path. After cutover this bug matters for the Expo Android app.
- Smallest fix here: when the article already has outbox rows, enqueue instead of sending live; and delete a drained row only if its payload is unchanged.
