## Part A — X6: rows are marked in-flight and no query ever selects them again

**This corrects the original task's premise.** The note below previously read "single-replica today, so there is no active bug". That is **wrong**: there is a live, replica-count-independent bug. A row is marked in-flight, the work fails or the process dies, and *no query in the system will ever select that state again*. The retry machinery downstream is therefore **unreachable — these services have retry logic that provably never runs.**

| Entity | Marked as | Selector reads | Result |
|---|---|---|---|
| `feed_items` | `processing` | `pending` | stranded forever; retry ladder dead |
| `raw_emails` | `processing` | `pending` | stranded forever; both retry caps unreachable |
| `content_outbox` (read/fetcher) | `sending` | `pending` | stranded **and** double-delivered |

Confirmed selectors at `a6c56a1`:
- `services/read/fetcher/internal/repository/feed_item.go:332` — `WHERE processing_status = 'pending'`
- `services/read/fetcher/internal/repository/outbox.go:164` — `WHERE delivery_status = 'pending' AND next_retry_at <= $1`
- `services/read/email/internal/repository/raw_email.go:140` — `WHERE processing_status = $1 AND retry_count < 5`, called with `models.ProcessingStatusPending` only

### Two proofs this is a known-good pattern the codebase already solved once

1. **The email service's own outbox is correct**, and sits in the sibling file of the broken raw-email selector in the same package — `services/read/email/internal/repository/outbox.go:142-160`:
   ```sql
   WHERE delivery_status IN ($1, $2)      -- DeliveryStatusPending, DeliveryStatusSending
     AND next_retry_at <= $3
     AND retry_count < max_retries
   ```
   Copy this shape. It is the in-repo reference pattern (strategy §2.3) — do not invent a new one.

2. **The email migration already anticipated the right selector.** `services/read/email/migrations/000001_initial_schema.up.sql:74` creates an index:
   ```sql
   WHERE processing_status IN ('pending', 'processing');
   ```
   **No query in the codebase can use it.** The schema author got it right; the query was never written to match.

## Part B — Theme 4: no atomic claim anywhere

No `FOR UPDATE SKIP LOCKED` or atomic claim-and-update appears **anywhere** in the codebase. Every worker does `SELECT ... WHERE status='pending'` and then flips status afterward (`repository/feed_item.go:322-338`, `outbox.go:157-170`, `feed.go:292+`). Multi-replica operation therefore causes duplicate fetches, duplicate outbound traffic to third-party sites, and last-writer-wins races on feed error/tier tracking. Prerequisite for ever scaling past one replica.

## Why the two halves are one task

**Shared risk:** widening a selector to include `processing`/`sending` without an atomic claim means two workers (or one worker and one stranded row's retry) select the same row and process it twice. `content_outbox` already double-delivers. So the selector and the claim change together, under **one decision** on the recovery mechanism:

- **`FOR UPDATE SKIP LOCKED`** — simple, correct within a transaction, but a crashed process's lock dies with its connection and the row returns immediately (fine) while an *in-progress* long fetch holds a transaction open for its duration (less fine).
- **Lease / visibility timeout** — add a `claimed_at`/`lease_expires_at` column, select `pending` OR (`processing` AND lease expired). Survives process death without holding a transaction open, but needs a migration.

Pick one, apply it consistently to all three entities, and **state the choice and its reasoning in the PR**.

## What to do
1. **Failing tests first**, per entity — both behaviours:
   - *Recovery:* mark a row in-flight, simulate the worker dying, assert a subsequent poll re-selects it and the retry ladder advances. Fails on main (row is stranded).
   - *Exclusivity:* two concurrent claimers against the same pending set, assert claims are **disjoint**. Fails on main.
2. Decide lease vs `FOR UPDATE SKIP LOCKED` (above). One decision, all three entities.
3. Widen the selectors to include the in-flight state, gated on the retry caps, following the email-outbox reference shape.
4. Add the atomic claim in the **same** change as each widened selector.
5. Verify the previously-unusable email index (`migrations/000001:74`) is now actually used by the new raw-emails selector (`EXPLAIN`), or drop it if the chosen shape differs.

## Done when
- Per entity: a crashed in-flight row is re-selected and retried (test fails on main), and concurrent claimers never claim the same row (test fails on main).
- No entity is left with a widened selector but no atomic claim.
- The retry ladders in all three services are demonstrably reachable.
