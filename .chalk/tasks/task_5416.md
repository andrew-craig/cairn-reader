**Touches:** services/read/fetcher (`GetPendingItems`, `GetPendingEntries`, `GetFeedsDueForPolling`), services/explore/fetcher (`GetNextFeed`), services/read/email outbox
**Blocked by:** the Wave 3 integration-CI task — this fix is only provable at that tier and will rot without it.

## Problem
No `FOR UPDATE SKIP LOCKED` or atomic claim-and-update appears **anywhere** in the codebase. Every worker does `SELECT ... WHERE status='pending'` and then flips status afterward (`repository/feed_item.go:322-338`, `outbox.go:157-170`, `feed.go:292+`).

Single-replica today, so there is no active bug — and `go test -race` is clean because the race is between *processes*, not goroutines. But running any worker with more than one replica, which is normal for HA, causes duplicate fetches, duplicate outbound traffic to third-party sites, and last-writer-wins races on feed error/tier tracking. This is a prerequisite for ever scaling past one replica.

## What to do
1. Integration test: two concurrent claimers against the same pending set; assert the claims are **disjoint**. Fails on main.
2. Add `FOR UPDATE SKIP LOCKED` to every claim query in the three workers.

## Done when
- Concurrent claimers never claim the same row, proven by an integration test in the CI integration job.
