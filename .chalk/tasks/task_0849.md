**Touches:** services/read/email/internal/worker/outbox_worker.go, services/read/fetcher workers, circuit-breaker code in both services

## Problem
None of the review's critical bugs can be *detected* in production, only reconstructed after a user complains:

- The **outbox worker** emits its "delivering batch" log only when work exists, has **no liveness heartbeat**, and has **no `recover()`** around its loop — a panic kills the process silently.
- Silent feed-batch failure has no "feeds polled per hour" counter.
- **Circuit-breaker state changes** — the loudest "downstream is down" signal — are logged via raw `fmt.Printf` in both services, invisible to any level-based alert.

## What to do
1. Heartbeat log per worker tick, **even when idle**, in the outbox and fetcher workers.
2. `recover()` per loop iteration so one bad entry cannot kill the process.
3. Replace `fmt.Printf` circuit-breaker logging with slog at WARN on state transitions.
4. Tests: assert a heartbeat is emitted on an idle tick; assert a panicking iteration is recovered and the loop continues.

## Done when
- A wedged or panicking worker is visible from logs alone, proven by tests.

## Review (2026-10-05)
- **email** (`internal/worker/tick.go` new): `runTick` wraps each Start-loop tick in both the outbox and email-processor workers — `recover()` → ERROR "worker tick panicked" with stack, else INFO "worker heartbeat" (worker, entries) on every tick incl. idle. Per-entry recover in the outbox `deliverBatch` loop and per-email goroutine in the processor (a goroutine panic can't be caught by the tick recover). Lead review caught that without per-entry recover a poison outbox entry (re-claimed first by `created_at`, never bumps `retry_count`) would strand its batch-mates indefinitely — fixed.
- **fetcher**: outbox poller and poll scheduler recover per tick and log INFO "Outbox poll tick" (fetched, queued) / "Poll scheduler tick" (due, polled) every tick; delivery goroutines recover per entry.
- **both**: circuit-breaker `OnStateChange` `fmt.Printf` → `slog.Warn` (name, from, to).
- Tests: idle heartbeat, panicking tick recovered + loop continues, panicking entry doesn't block the next, CB WARN. Lead independently reverted the source files to HEAD and confirmed every new test fails, then passes with the fix. `go build/vet`, `go test -race` clean in both modules.
- Known residual: a panicking entry is not recorded as a delivery failure, so it re-panics after each lease expiry (10 min) — now loudly visible at ERROR rather than silent. Heartbeat at INFO is ~1 line/tick per worker (5–10s intervals); downgrade if log volume is a problem.
