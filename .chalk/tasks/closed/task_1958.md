## Problem
The users service's DB-backed tests cannot run, for **two independent reasons** — fixing either one alone leaves them dead:
1. **No Postgres in CI.** `.github/workflows/go-checks.yml`, job `test-users`, runs `go test ./internal/...` with **no `services: postgres` block** — unlike `test-integration-read`, which provisions postgres:16-alpine and sets TEST_DB_*. Any test needing a database cannot pass.
2. **The env helper is a stub.** `getEnvOrDefault` is triplicated across three files and **ignores `os.Getenv` entirely**:
   - services/users/internal/database/user_repository_test.go:43
   - services/users/internal/services/auth_service_test.go:80
   - services/users/internal/handlers/auth_handler_test.go:104
   All three bodies are literally:
   ```go
   // In real implementation, use os.Getenv
   return defaultValue
   ```
   So even with a Postgres service container and TEST_DB_* exported, the tests would still dial the hardcoded defaults and ignore the CI environment.

## What to do
1. Add a `services: postgres` block to `test-users`, mirroring `test-integration-read`'s (health-cmd pg_isready, TEST_DB_HOST/PORT/USER/PASSWORD env).
2. Replace all three `getEnvOrDefault` copies with one real implementation that reads `os.Getenv`. Prefer reusing the existing shared helper over a fourth copy — see task_7ada (pkg/env vs pkg/config consolidation) and don't fight it.
3. Expect red on first enablement — that is the finding, not a regression. Triage what fails.

## Review

Re-verified both problems on `main` before starting - confirmed as described.

1. Added the `services: postgres` block to `test-users` (mirrors `test-integration-read`: postgres:16-alpine, `POSTGRES_DB: cairn_test`, pg_isready healthcheck) plus a "Run migrations" step (`go run cmd/migrate/main.go -command=up`) so the schema exists before tests run - the DB-backed tests connect directly, they don't self-migrate.
2. Replaced all three `getEnvOrDefault` stubs with `pkg/env.GetString` (already an indirect dependency of `services/users` via the root module replace directive; already used elsewhere in this service, e.g. `internal/config/config.go`) - no fourth copy added, per the task's own instruction and task_7ada.

**Enabling exposed three additional, pre-existing bugs that were blocking the suite from actually executing** (not silently skipped, not this task's two named causes, but direct blockers of "tests actually execute" - fixed in the same PR because leaving them meant the test binary panicked/crashed rather than ran):

- `internal/handlers` (`auth_handler_test.go` + `user_handler_test.go`, ~20 call sites): every response-decoding call unmarshalled the raw handler response into the inner type (`services.AuthResponse` / `models.User`) instead of unwrapping the `pkg/api` `{data,meta}` success envelope every handler actually writes via `api.WriteSuccess`. Since `AuthResponse.User` and several `models.User` fields are pointers, this null-decoded and panicked (nil deref) on first real execution, aborting the whole test binary before most tests ever ran - the exact X9 symptom this task targets. Fixed by adding a small `decodeAuthResponse`/`decodeUser` helper (mirroring the correct envelope-unwrap pattern already present twice in `auth_handler_test.go`) and repointing every call site at it.
- `internal/handlers/user_handler_test.go`: 28 call sites built `chi` route context with param key `"id"`, but `router.go` registers `/{user_id}` and the handlers all read `chi.URLParam(r, "user_id")` - every one of these requests 400'd on "invalid user ID format" instead of exercising the intended path. Fixed by correcting the param key (two pre-existing call sites already used `"user_id"` correctly and were left alone).
- A handful of assertions were simply wrong once actually evaluated: `resp.User.Email` compared as `string` when `models.User.Email` is `*string` (4 sites, fixed by dereferencing); expected-substring checks for `"invalid request"` that don't match the handler's actual validation messages (`"email and password are required"`, `"expo_device_id is required"` - 3 sites, fixed to match); and two `TestUpgradeAccount` assertions (`PasswordHash`, `IsHybrid()`/`IsMobileOnly()`) that can never pass via a decoded HTTP response because `models.User.PasswordHash`/`ExpoDeviceID` are `json:"-"` by design - fixed by reading the row back from the DB via `UserRepository.GetUserByID` instead.
- CI job (`go test ./internal/...` with no `-p`): all these packages share one physical Postgres service container via literal test data (emails, device IDs). Go's default package-level parallelism raced different packages' test binaries against that one DB and produced spurious "already exists" / assertion failures depending on scheduling. Added `-p 1` to force sequential package execution - confirmed this alone (with the fixes above) gets the suite deterministically green apart from the one genuine bug below.

**One genuine, pre-existing production bug remains and is intentionally left red, per this task's own "pass or triaged failures" bar** - filed as **bug_f53a**: `internal/auth/jwt.go`'s `GenerateToken` has no `jti`/uniqueness claim, and RS256 (PKCS#1v1.5) signing is deterministic, so two access tokens minted for the same user within the same wall-clock second are byte-identical - defeating token rotation. Reproduces deterministically (5/5) in `TestAuthService_RefreshAccessToken/success` and intermittently (timing-dependent) in `TestAuthService_Login/success`. Not fixed here - it's a distinct, separately-scoped finding (JWT generation logic, not CI/test-infrastructure), tracked in bug_f53a with a recipe (add `jti`).

**Verification:** `gofmt -l .`, `go vet ./...`, `golangci-lint run ./...` all clean. `go test -race -p 1 -count=1 ./internal/...` against a locally provisioned Postgres 16 (matching the CI job exactly, including the migration step) is green except the one tracked `bug_f53a` failure.
