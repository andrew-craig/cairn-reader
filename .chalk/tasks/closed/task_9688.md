## Problem
Sentinel-to-HTTP-status mapping is open-coded as **43 `errors.Is` branches** spread across:
- `services/users/internal/handlers/auth_handler.go`
- `services/users/internal/handlers/user_handler.go`

Every new sentinel means another branch in another handler, and a missed one falls through to 500.

## Scope note — the mapping table does not exist yet
The audit names a "sentinel→HTTP mapping table". **That is the proposal, not an existing symbol** — there is nothing to find or consolidate onto. The work is to create it.

## What to do
1. Add `services/users/internal/handlers/errors.go` with an **ordered** table plus a `writeServiceError` helper.
   **It must be ordered, not a map:** `errors.Is` cannot be a map key — matching is a predicate, not equality — so the table is a slice walked in order, and order encodes precedence between overlapping sentinels.
2. Repoint both handlers onto `writeServiceError`.
3. Assert on the full mapping in a table-driven test, so a new sentinel without a mapping fails loudly rather than becoming a 500.

## Blocked by task_9680 — do not start first
task_9680 is **one specific sentinel mismatch inside this same finding** (the audit's F-S14-1):
- `services/users/internal/services/refresh_token.go:152` returns the **JWT** package's `ErrTokenExpired`
- `services/users/internal/services/auth_service.go:431` tests for `apperrors.ErrTokenExpired`
- `errors.Is` therefore **never matches** — currently masked by a `strings.Contains` fallback at `auth_handler.go:362`

If the table is built first it will **encode the broken mapping** and the `strings.Contains` crutch will look load-bearing. Fix task_9680, then build the table on correct sentinels.

## Done when
- Both handlers map sentinels through one ordered table, no `strings.Contains` error sniffing remains, and the mapping is covered by a table-driven test.
