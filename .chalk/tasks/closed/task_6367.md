## Context

The real self-hosted Cairn Postgres volume was wiped yesterday by a CI job
collision (fix tracked separately). Investigation found there was no actual
backup in place: docs describe a `scripts/backup.sh` + cron pattern but it
was never wired up on this host — no crontab entry, no dump files anywhere.

## Plan

1. Add `infrastructure/docker/selfhost/scripts/backup.sh` — `pg_dumpall` via
   `docker compose exec -T cairn-db`, gzip, 30-day retention cleanup. Use the
   real service/user names from `docker-compose.yml` (`cairn-db`, user
   `cairn`), not the generic `postgres` name from `docs/DEPLOYMENT.md`'s
   template. Resolve the compose file location from the script's own path so
   it works regardless of invocation cwd, and never touches another
   Postgres container on this shared host.
   → verify: `bash -n` syntax check, manual dry run against the live stack.
2. Install on this host: create `/home/operator/cairn-backups/` (outside the
   git repo), add a nightly 2am crontab entry for `operator` pointing at the
   script's real path in this checkout, logging to a file inside the backup
   dir.
   → verify: `crontab -l` shows the entry.
3. Run the script manually once to confirm it produces a valid, non-trivial
   gzip dump against the live `cairn-selfhost` stack (if the stack is up).
   → verify: `gzip -t` on the resulting dump file, non-trivial file size.

## Results

- Added `infrastructure/docker/selfhost/scripts/backup.sh`: dumps via
  `docker compose --project-directory <selfhost dir> -f docker-compose.yml
  exec -T cairn-db pg_dumpall -U cairn | gzip`, writes to a `.tmp` file
  first and only `mv`s it into place on success (a first manual run against
  the down stack showed the naive `... > file.sql.gz` form silently leaves a
  20-byte empty gzip behind when `pg_dumpall` fails — fixed by promoting the
  dump only after the pipeline succeeds). Retention: deletes
  `cairn_all_*.sql.gz` older than `RETENTION_DAYS` (default 30). Compose
  invocation directory is resolved from the script's own path
  (`$BASH_SOURCE`), so it works from any cwd and can't collide with another
  Postgres container on this shared host — verified by exercising it against
  a throwaway `cairn-db`-named compose project in `/tmp` (dump succeeded,
  gzip validated, retention pruning verified) and confirming the real
  `cairn-selfhost_*` volumes were untouched throughout.
- Added a short "Automate it" note to `infrastructure/docker/selfhost/README.md`
  pointing at the script.
- Installed on this host: backup dir `/home/operator/cairn-backups/`
  (outside the repo), crontab entry for `operator`:
  `0 2 * * * BACKUP_DIR=/home/operator/cairn-backups
  /home/operator/cairn-reader/infrastructure/docker/selfhost/scripts/backup.sh
  >> /home/operator/cairn-backups/backup.log 2>&1` — confirmed present via
  `crontab -l`.
- Manual run against the real `cairn-selfhost` stack: the stack currently
  has **no containers running at all** (`docker compose ... ps` returns
  empty, consistent with the ongoing incident/fix in the other branch), so
  the live run correctly failed fast (`service "cairn-db" is not running`)
  and logged to `/home/operator/cairn-backups/backup.log` with no bogus
  file left behind. Did not start the stack myself per instructions. Script
  correctness against a real running Postgres was verified via the
  throwaway compose project instead (valid, non-trivial `.sql.gz`,
  `gzip -t` passed).
