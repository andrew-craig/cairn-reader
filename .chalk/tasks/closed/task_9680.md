**Touches:** services/users/internal/services/auth_service.go:441

## Problem
A dead `errors.Is(err, apperrors.ErrTokenExpired)` branch means routine token expiry logs at **ERROR**. Root-caused precisely: the validator returns `auth.ErrTokenExpired` (`jwt.go:21`), the branch compares against `apperrors.ErrTokenExpired` (`pkg/errors/errors.go:53`) — different sentinels, so the branch never matches. Normal expiry logs at ERROR forever, and with no metrics backend anywhere in the repo, the elevated error rate cannot be separated from a real spike. Error-rate monitoring is useless until this is fixed.

## What to do
1. Test first: expire a token, assert the log level is INFO/WARN. Fails on main.
2. Compare against the sentinel the validator actually returns; log routine expiry at INFO or WARN.
3. Grep for other `errors.Is` comparisons against the wrong package's sentinel while you are in there — same class of bug.

## Done when
- Routine expiry no longer logs at ERROR, proven by a level assertion in a test.

The audit author pinned the three points, which saves step 2's search:

1. `services/users/internal/services/refresh_token.go:152` **returns** the JWT package's `ErrTokenExpired`
2. `services/users/internal/services/auth_service.go:431` **tests for** `apperrors.ErrTokenExpired`
3. `errors.Is` therefore **never matches** — and the failure is masked by a `strings.Contains` fallback at `services/users/internal/handlers/auth_handler.go:362`

The `strings.Contains` crutch is the reason this looks like it works. Removing it is part of the fix, not a follow-up — otherwise the next reader will assume the sentinel comparison is what's doing the work.
