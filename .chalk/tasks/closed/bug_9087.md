The outbox worker calls Content Service BulkCreateContent and expects the response to populate Created, Existing, or Failed slices. In practice the response has none of these populated, so every entry hits the fallback branch at services/read/fetcher/internal/worker/outbox_worker.go:218-223 and logs:

  Unexpected response from Content Service worker_id=N

The entry is then handed to handleDeliveryFailure, which then hits the separate enum-cast bug (bug_4e3c).

Discovered while validating user-subscribed RSS fetch (PR #196). Latent until the upstream NoOpFeedProcessor was replaced — once real items started flowing into the outbox, every delivery attempt failed. 59 outbox entries on one local run, all stuck in 'sending' status.

Likely causes (need investigation, do not implement without confirming):
1. Field-name mismatch between client decode struct (services/read/fetcher/internal/client/content_service_client.go) and the actual JSON keys returned by Content Service POST /api/v1/content/bulk
2. Endpoint path mismatch — commit bcdddad already corrected paths once; verify selfhost wiring at adapt_ingest_rss.go points ContentBaseURL at the right base path
3. Content Service is rejecting payload at validation time and returning a 4xx body that doesn't match the expected BulkResponse shape

Investigation first steps:
- Capture an actual HTTP response by running the selfhost stack with at least one subscribed feed and either tcpdump'ing the loopback exchange or adding a debug log of resp.Body in the client
- Compare returned JSON against the Created/Existing/Failed struct tags used to decode it
- Verify selfhost ContentBaseURL/InternalAPIKey wiring (cmd/selfhost/adapt_ingest_rss.go)

Files:
- services/read/fetcher/internal/worker/outbox_worker.go (line 196 onward)
- services/read/fetcher/internal/client/content_service_client.go
- services/read/content/internal/api/ (BulkCreateContent handler)
- cmd/selfhost/adapt_ingest_rss.go (ContentBaseURL config)
